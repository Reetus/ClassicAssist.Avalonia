# Hotkey command TODO

Gap between this repo and the WPF `ClassicAssist` tree. Generated by comparing every
`[HotkeyCommand]`-attributed class in both trees.

- **79 hotkey commands upstream, 74 here**
- **5 missing** (13 as of writing; `Grid Container Viewer`, `All Names`, `Object Inspector`,
  `Use Last Skill`, `Greater Heal / Cure Self` and `Mini Heal / Cure Self` have since been ported)
- No command here is absent upstream, and no signature has drifted - the gap is purely
  commands that were never ported.

Names below are the `Name =` on the attribute, which is also the resource key. Every one of
them already has an entry in `Strings.resx`, so nothing here needs a new string.

## Blocked on configurable-hotkey infrastructure

Nothing left here - the infrastructure was built alongside these two, so any future configurable
hotkey only needs the attribute on a property.

- [x] ~~**Greater Heal / Cure Self**~~ (`GreaterHealCureSelf.cs`)
- [x] ~~**Mini Heal / Cure Self**~~ (`MiniHealCureSelf.cs`)

      The command bodies ported as-is. The mechanism behind them:

      - `HotkeyConfigurationAttribute` and the `CureType` enum ported verbatim.
      - `HotkeyEntry.Configurable` added, gating both `ConfigureHotkeyCommand`'s `CanExecute` and
        the Options button on the Hotkeys tab.
      - `HotkeysTabViewModel` reads and writes the `Hotkeys/Options` array in the same
        Type/Property/Value shape WPF uses, so a profile shared between the two round-trips.
        `ProfileRoundTripTests` no longer defers `Hotkeys.Options` and covers exactly that.
      - The dialog is `HotkeyOptionsWindow` + `HotkeyOptionsViewModel`. WPF assembles its Grid of
        label/ComboBox pairs in code-behind; this binds an `ItemsControl` to a list of rows the
        view model reflects out, which keeps the layout in XAML and the dialog unit-testable.

      Two deliberate divergences from upstream, both about not failing silently: a stored property
      that no longer resolves is skipped rather than dereferenced outside the `try` (upstream
      takes the whole hotkey load down), and an enum label with no `Strings` entry falls back to
      its `[Description]` rather than throwing out of the dialog constructor.

## Notes for whoever picks this up

- A hotkey's `Name` is looked up in `Strings.ResourceManager` by `HotkeyCommand`'s constructor and
  falls back to the literal if absent, so a typo shows up as an untranslated string rather than an
  error. Check the key exists.
- An empty `Category` puts the command under `Commands` in the tree, not in a blank group.
- Commands are discovered by reflection over `Assembly.GetExecutingAssembly()` in
  `HotkeysTabViewModel.Deserialize`, so a new file in `Data/Hotkeys/Commands/` is picked up with no
  registration step.
- `Execute()` runs on a thread pool thread (`Action = hs => Task.Run( Execute )`). Anything that
  touches the UI has to go through `Engine.UIInvoker`, and anything that blocks on a target or a
  packet wait is fine there.
